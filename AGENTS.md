# AI Agent Instructions

These rules apply to all AI-generated contributions in this repository. This file holds what every task needs and an
index of topic guides: open the guide for the area you work in before starting. Keep this file short. New detail goes
into the topic's own document, with at most one index line here.

## Core Rules

- Generate new code. Never copy code from OpenEnroth or mm_mapview2. Use the local `reference/OpenEnroth-git/` (not
  the web) and mm_mapview2 only as behavioral/structural references.
- GrayFace's decompiled scripts in `reference/mmext-scripts/Decompiled_Scripts/` are semi-authoritative MM6/MM7/MM8
  event behavior references (the per-world `txt/` folders read best when checking or repairing exported EVT Lua). Use
  them to understand intent and validate behavior; never copy script code into OpenYAMM.
- Never edit Lua event files generated by the Lua exporter (headed `-- generated from legacy EVT/STR`): fix the
  exporter or add an explicit event-file-specific override/overlay. Regenerate with `tools/regenerate_lua_events.sh`
  (shared `assets_dev/engine/events/Global.lua` once from the MM8/default source, then MM6/MM7/MM8 map-local scripts
  with `--skip-global`).
- MM9 map Lua and scene files (`assets_dev/worlds/mm9/events/maps/<stem>.lua`, `<stem>.scene.yml`, `.blv`) are written
  by each map's converter in `level_generation/projects/mm9r_<map>*/`: never edit only the installed file. Follow
  [MM9 generated map files](devdocs/agents/MM9_GENERATED_MAP_FILES.md) (change the converter, scratch build, diff,
  install into `assets_dev` and the review root; `tools/mm9_import_discovery/check_mm9_map_lua.py` before and after).
  The hand-written MM9 Lua (`worlds/mm9/events/common/mm9_common.lua`, `worlds/mm9/behaviors/*.lua`) is edited directly.
- Prefer simple, maintainable solutions over clever abstractions. Do not add adapter/forwarding layers that only hide
  duplicated ownership.
- Keep temporary diagnostics and noisy logs out of final changes.
- Do not add hack fixes or broad compatibility fallbacks that mask stale/broken state. Fix the authoritative data,
  event script, schema, or system behavior instead; if old saves/assets need migration, make that an explicit migration.
- If a task explicitly names planning documents, follow them for that task only; stale plans are not global
  instructions.
- When the user explicitly asks for mockups, also build an HTML viewer page without being asked: one page that shows
  every mockup live (scaled to fit, with a link to full size), switches between them and their states, lists what each
  shows and includes the captures. Keep it beside the mockups (`viewer.html`), publish it as an Artifact with the
  mockups' files and give the user its link. Delegated mockup work includes the viewer.
- When the user references an image by filename or bare id (`901.png`, `901`), first resolve it as `test_img/901.png`.
- Start searches in relevant source directories; include `reference/`, `mm9/`, generated assets and build trees only
  when needed.

## Coding Style

- C++20. Maximum line length: 120 characters. Braces on new lines.
- Naming: classes `CamelCase`, methods/variables `camelCase`, members `m_variable`; pointers `pPointer`, member
  pointers `m_pPointer`.
- Prefer const correctness and minimal headers.
- Prefer explicit types over `auto`; use `auto` only when it clearly improves readability or is effectively required.
- Do not use `[[nodiscard]]`.
- Prefer unqualified integer and size types: `uint32_t`, `int16_t`, `size_t`.
- Avoid raw `new`/`delete`, global state, unnecessary macros, and unnecessary `static_cast`.
- Always use `override` where applicable.
- New player-visible text in C++ goes through `Engine::tr()` (or `trn()` for counts) with named `{placeholders}`, never
  a sentence built from pieces; Lua passes whole sentences to `evt` functions or uses `tr()`. Data tables and generated
  event scripts stay English ([Localization](devdocs/LOCALIZATION.md)).

```cpp
if (condition)
{
    doSomething();
}
```

## Architecture

Subsystem layers: `engine/`, `game/`, `core/` (the code the game shares with Map Studio, `openyamm-studio/`: map
formats, scene files, collision and the map builds in `core/compile/`; see `core/CMakeLists.txt`) and `tools/`. Map
Studio reuses `core/` and must not duplicate gameplay logic.

Treat gameplay systems as shared by default. Fixes for HUD, UI screens, input/keybind semantics, inventory, items,
dialogue, shops, chests, rest, spell casting, projectiles, particles, combat rules, monster AI, party state, qbits,
journal, save/load, audio reactions, and gameplay FX should normally live in shared gameplay code.
Indoor/outdoor-specific code is limited to BLV/ODM world representation: map loading, geometry rendering,
visibility/culling, picking and LOS, collision, floor resolution and movement integration, projectile collision against
world geometry, event-face/decor/mechanism lookup and world-specific decal placement. If a bug appears only indoors or
only outdoors, first check whether the shared system is called with different data or missing world hooks; fix the
shared path or the world hook rather than adding divergent logic to `IndoorGameView` or `OutdoorGameView`.

Rendering uses bgfx and stays simple (static meshes, sprites/billboards, UI, basic lighting, fog). Audio is SDL3 with an
engine mixer layer (effects, music, volume groups, fades). Video is FFmpeg OGV with audio/video sync and looping.

### Flat Base, World, And Mod Content

- OpenYAMM is the engine. Worlds (MM6, MM7, MM8, MM9, Xeen, custom settings) are mounted content packages, not separate
  engines or hardcoded runtime modes. Implement world support around existing runtime systems through package mounting,
  world and mod manifests, declared id ranges and active-world context; do not rewrite the engine for it.
- Flat MMerge-like base: `assets_dev/engine/` is the global/base layer; `assets_dev/worlds/*` holds world-local maps,
  events and presentation. MM6/MM7/MM8 worlds must not own active TXT/BIN gameplay tables: the merged tables live under
  `assets_dev/engine/`. No separate campaign package layer. The base decides which worlds are mounted, which can start a
  new game, and how cross-world travel, metaquests, difficulty profiles and global overrides work.
- Engine/base scope: what the party can carry or what defines base mechanics (items, skills, spells, classes, races,
  portraits, paperdolls, formulas, base state, the merged QBit journal registry `quests.txt`) and the merged
  journal/autonote/history/NPC dialogue, house, travel, monster, decoration and object registries. World scope:
  geography and map-local content (maps, map events, map/local event vars, loading screens, monster art, presentation).
- Rulesets (Standard MMMerge, MAW, later vanilla MM6–MM8) are packages under `assets_dev/engine/rulesets/<id>/` with a
  `ruleset.yml` (inside the engine package, so released updaters accept their packs). A ruleset may override cells
  of, or replace, named tables in `assets_dev/engine/data_tables/` through its own patch files (the agreed exception
  to "worlds must not own gameplay tables"). Never edit the engine tables for a ruleset.
- QBits are global party/save state. Worlds and mods may own declared QBit ranges (custom content from `10000+`); they
  merge into the shared registry and must not silently collide. Use canonical namespaced ids for world-specific data;
  MM6/MM7/MM8 raw ids are import aliases, not global truth.
- A world's own decorations (rows in its declared range, sprites, bindings) go in its world package, never into the
  engine's `decoration_data.txt` ([World decoration contributions](devdocs/WORLD_DECORATION_CONTRIBUTIONS.md)).
- MMerge references (`reference/mmerge_data_forus/`, `reference/mmmerge/`) are data and behavior references only;
  import into the world/mod architecture instead of reproducing MMerge's memory-hook runtime.
- MM9 must not regress MM6/MM7/MM8 gameplay, data behavior, save/load, rendering, asset lookup, stability, startup or
  map-loading time, memory use or performance. Keep MM9 work world/mod-scoped; unmounted, it adds no meaningful runtime
  cost. Validate affected MM6/MM7/MM8 paths alongside MM9.

## Assets And Runtime

- Keep original asset formats whenever practical: TXT gameplay data, WAV audio, MP3/FLAC music, OGV video, ZIP packages.
  Development assets live under `assets_dev/`; runtime packages under `assets/*.zip` and `assets/worlds/*.zip`.
- 3D models: the accepted GLB is a source in `assets_source/...`; install only with `tools/install_model.py`, never by
  copying into `assets_dev`, and never edit, re-export or copy back from an `assets_dev` model. Where MM6–MM8 and MM9
  decorations are installed and bound, the winding check and backface split:
  [Installing 3D models](devdocs/agents/ASSET_GENERATION.md#installing-3d-models).
- Icons: restored global icons in `assets_dev/engine/icons_x2`, MM6–MM8 NPC portraits in
  `assets_dev/worlds/mm*/icons_x2`, MM9's in `worlds/mm9/icons_x2` (installed by
  `tools/mm9_import_discovery/install_mm9_item_art_x2.py` and `import_mm9_items.py`); lowercase filenames, 0644
  permissions; `engine/icon_packages.txt` declares the tiers. Originals are archived in `assets_legacy/icons_20260926/`;
  do not repopulate the retired `icons` folders (receipts:
  `level_generation/ui/hud_inventory/runtime_install_20260926/README.md`).
- The game does not check whether an outdoor lighting bake is older than its sources. Before a release or commit, run
  `tools/lighting/stale_bakes.py` and re-bake what it lists (`tools/lighting/baked_outdoors/README.md`).

## Build, Test And Run

- **Heavy jobs and memory.** Several sessions and their agents share this PC (121 GB RAM, 8 GB swap). On 2026-11-22
  three MM9 conversions, two C++ builds and game runs overlapped, filled RAM and swap, and the PC locked up until a
  power cycle. Run every heavy job through `tools/heavy.sh <cap GB> <command...>`: it waits until the cap plus a
  24 GB reserve is free and kills the job alone if it goes over its cap. Caps: a C++ build 24 (with `-j16`), a MM9
  map conversion 48 (`mm9r_common/lane.sh` does this), a Blender bake 16, an oymap map build 8, a game run or
  playthrough 6. An orchestrator runs at most three agents that start heavy jobs at once.
- **Stopping processes.** Never kill a process's parent or grandparent, and never kill a PID you have not just checked
  with `ps -o pid,ppid,cmd -p <pid>`. Kill only PIDs whose command is your own worker (game, scenario, build, bake,
  script), never `systemd`, `bash -l`, `tmux`, `claude`, a terminal or anything whose command you did not start; prefer
  the exact PID you saved at launch or `timeout`. On 2026-11-25 an agent ran `kill $PP $P <pid>` on a scenario run
  started with `systemd-run`: the grandparent was `systemd --user`, and it logged the user out and ended every session.
- Build: `tools/heavy.sh 24 cmake --build build --target openyamm -j16`. Unit tests (prefer doctest for pure logic):
  target `openyamm_unit_tests`, then `./build/tests/openyamm_unit_tests --test-case='*pattern*'`. Runtime/map behavior:
  `./build/game/openyamm --headless-run-scenario <scenario.yml>` (examples in `tests/scenarios/`).
- Do not run Vulkan builds or rebuilds (including `build-vulkan/`) unless the user explicitly requests them for the
  current task; earlier authorization does not carry forward.
- Story and quest playthroughs (`tests/playthrough/mm9/`, its `promotions/`, `tests/scenarios/mm9/side_quests/`) are
  long checks, never CI and not routine: [when to run them](devdocs/agents/PLAYTHROUGHS.md).
- Game runs: `./tools/run_game.sh --isolated <unique name> ...` (starts minimized; `--visible` only for FPS work or when
  the user asks), engine-native screenshots and tours, waiting on your run's exact PID (never `pgrep -f`), the user's
  standing approvals for the run, capture and profiling wrappers: [Game runs](devdocs/agents/GAME_RUNS.md).
- Android: test with a release APK; a debug APK only when the user asks or instrumentation requires it.
