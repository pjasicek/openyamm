## What exists

**Transactions and history (`core/Ops`).** `oymap edit` applies a list of operations (`add`, `set`, `remove`,
`set_value`) as one transaction: all or nothing, with a dry run, an expected revision, and the check delta (issues
introduced and fixed). A change that introduces issues is refused unless allowed. The revision is a hash of the
project's canonical files. `.oymap/` (ignored by git through its own `.gitignore`) holds the last state the tool
saw and a history with the files before and after each change. An edit made with another tool is found on the next
read and recorded as an "outside" entry with its semantic diff; `oymap undo` and `redo` work on it like on any
transaction. The diff names objects and fields and shows plain values before and after
(`objects.yml: door:gate changed speed (64 -> 200)`).

**Overlay projects.** A project with `base: <shipped map>` (written by `oymap import`) changes that map without
owning it. A wiring event with `replaces: evt:e20` takes the handler of the base map's event 20; ids of the base
map's doors, events and sectors come from `ids.lock.yml`. `oymap build` writes `<map>_<project id>.lua`, which
replaces `evt.map[id]` only: timers, load events, titles and chest links of the event stay (the game's
`ReplaceMapEvent` drops timers, so the overlay does not use it). With `--assets` the build runs the overlay against
the base script in the sandbox. New presets: `teleport`, `script`; an overlay refuses `once: true` and named map
variables, because it has no numbers of its own to give them.

**Placeholders.** `objects.yml` `placeholders`: a place and a request (`stands_for`, `size`) for something no asset
exists for. Checked like any object, not built, and listed as a build warning every time.

**Asset search.** `oymap assets <words>`: decorations (name, hint, radius, height, light) and face textures with
their sizes in texels; every word must match.

**`oymap serve` and the host.** `oymap serve` answers JSON-RPC on standard input and output (`run` a command, get
its exit code and output). `openyamm-studio/host` is a Node process over it with no map logic and no state:

- an MCP server over stdio with fourteen tools: `map_open`, `map_overview`, `map_edit`, `map_validate` (always
  loaded), `map_query`, `map_flow`, `map_render`, `map_assets`, `map_api`, `map_build`, `map_playtest`, `map_pins`,
  `map_history`, `map_exec`;
- a WebSocket endpoint for the browser editor: 127.0.0.1 only, an allow list of origins and a pairing token
  (tested: refused without the token, with a wrong one, and from another origin);
- `call.mjs`, one tool call from a shell through the same server, for agents without an MCP connection.

**Review pins.** `review/pins.yml`: notes pinned to an object or a space, resolved with a reply (`map_pins`).

**The game's development mount (PLAN 10b item 1).** `--extra-mount <dir>`: a folder laid out like an asset root
whose engine files and worlds' `maps`, `events` and `textures` are read in front of a development root's. It is in
`engine/AssetFileSystem` (`mountExtraDevelopmentRoot`, `InstalledContentOptions::extraMountRoot`), `game/app/main.cpp`
and the scenario runner (which otherwise passes no content options on), with a unit test in
`tests/AssetFileSystemTests.cpp`. `oymap install --mount` writes such a folder; `oymap audit|flow|solve|render
--mount` read one. The slice dungeon and both overlays are played this way with nothing copied into a root.
**These are unstaged changes to `engine/`, `game/` and `tests/` for your review**, beside the S1 cuts.

## Not done, and why

- **Reload of the running map (PLAN 10b item 2).** It changes how the running game holds a map and should be its
  own reviewed change. A playtest starts the game again, which takes seconds headless; the browser's "Play here"
  (S5) is what will want it.
- **Streamable HTTP, jobs and MCP Tasks, output schemas, elicitation on undo.** No client here needs them yet; build
  and playtest answer within the call (the longest so far about 20 s; Codex stops a call at 60 s, so jobs become
  necessary when playtests grow). Recorded in PLAN section 8.
- **Operations for Populate and Dress beyond the generic ones.** `add`, `set` and `remove` cover every list of the
  schema; the plan's named operations (`road.add`, `terrain.raise` ...) belong to the authoring milestones that give
  them something to do (S3, S4). There is no `schema/ops/` catalogue; `map_api` topic "ops" documents the four.
- **Texture sizes from the catalogue as theme defaults.** The search reports them; themes still carry `size`.
- **An overlay cannot add** events, doors or objects to a shipped map, only replace handlers. Scene overlays
  (objects, spawns) are S3 work with the scene writer.

## Findings

- **The MCP SDK is 1.32.2, protocol 2025-11-25.** The research note's "SDK 2.x" and revision 2026-07-28 are not what
  npm ships (checked 2026-11-12). The plan and the note are corrected; nothing built relies on the newer revision.
- **The scenario runner ignores content options** (mods, language) on purpose; only the mount is passed through.
- **`ReplaceMapEvent` drops an event's timers.** Found when an overlaid Goblinwatch lost a timer; the overlay now
  assigns the handler itself.
- **An engine log line on standard output breaks a tool that prints JSON there.** The mount is therefore silent in
  the engine; the game's list of mounted search paths shows it.
- **Other sessions build the game without the build lock**, which once left a half-written library and a failed
  link here. A second build fixed it.
- **The first tools let a wrong script through.** The flow showed only four arguments of a call and the sandbox
  accepted any function name, so an overlay could pass the build and fail in the game. The evaluation agents found
  both; see below.
- **Lua errors in the sandbox are mostly the sandbox's own** (its game functions return nothing): 460 across the 247
  shipped maps. Only three kinds are certain faults and are reported: a function the game does not have, a selector
  that is not a number, a call of something that is not a function. No shipped map has any of them.

## Agent evaluation v1

`openyamm-studio/eval/`: [tasks.yml](../../openyamm-studio/eval/tasks.yml) (eight tasks with checks) and
[RESULTS.md](../../openyamm-studio/eval/RESULTS.md) (the first run). Each task goes to a fresh agent that may use
only the tools: no studio sources, examples or tests, no game files. The agent's friction list is the product; the
check decides whether the task was done.

The first run (five agents' worth of tasks, all eight tasks done by their checks) cost about 85 and 75 tool calls
for the two rewires and produced some forty points of friction. The ones that made a wrong result possible were
fixed the same day: `map_flow` shows every argument; the build refuses calls to functions the game does not have
(the list is read from the game's own registration when the studio is built, so there is no second list to keep);
`map_query` no longer answers a list with the lock's table; a failing playtest shows its Lua error; a dry run no
longer looks like a new revision. The tools also gained reference text an agent had to guess before (what a
script may call, how to write a playtest, one list of a schema). What stayed open is listed in RESULTS.md with the
milestone it belongs to; the largest is that the wiring presets cannot yet say a gold or stat condition, which is
why the wells are five scripts.

A second run of the wells task against the fixed tools was done again in about 75 calls: no cheaper, but the agent
proved its overlay is what runs and the build stopped two wrong selectors. It also caught an error in the new
reference text (it named `VAR_` constants that do not exist), now corrected. The honest reading: the tools are
sufficient and safe against the mistakes seen so far, and still expensive, because an agent must find out by
trial how to write in Lua what the flow shows. Presets that cover gold, stats and autonotes, and a script
reference generated from the game's support script, are the next gain (S3).
